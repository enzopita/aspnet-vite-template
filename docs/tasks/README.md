# Tasks

A task is the **contract** between a planner (the orchestrator model of the day, or a human) and an executor agent
(any model, in any harness). Why it works this way: [ADR 0008](../adr/0008-agent-task-workflow.md).

## Lifecycle

| Status | Set by | Meaning |
|---|---|---|
| `ready` | planner | Spec committed on `main`, nobody working on it |
| `in-progress` | `task.mjs start` / executor | Executor working on `task/NNNN-slug` |
| `review` | executor | `verify` passed, work committed, Executor log written |
| `blocked` | executor | The spec can't be done as written; the Executor log says why |
| `changes-requested` | reviewer | Review findings are in `## Review`; the executor resumes on the same branch |
| `done` | reviewer | Merged into `main` |

```text
planner                 executor (task/NNNN-slug)                  reviewer
/plan-task ─► spec ─► task.mjs start ─► check … verify ─► commit ─► /review-task ─► merge or changes-requested
on main                                                              (polish, then merge)
```

## Commands

All of them are in `node scripts/agents/task.mjs help`. The ones you type:

- `start <id>`: create the sibling executor worktree (`../<repo>-task-NNNN` on `task/NNNN-slug`), write `agent-role = executor` in its git dir, set `status: in-progress`, and print the executor brief.
- `review <id>`: create the sibling reviewer worktree (`../<repo>-review-NNNN` on `review/NNNN-slug` branched from `task/NNNN-slug`), write `agent-role = reviewer`, and print the review instructions.
- `brief <id>`: print that prompt again.
- `check`: the **fence**: changed paths inside `allow`, protected files untouched, the spec unchanged apart from
  `status` and `## Executor log` (plus `## Review` on `review/*` branches). Runs on every commit of `task/*` and `review/*`
  branches and in the trusted `fence` workflow.
- `verify`: `check`, plus `scripts/verify.mjs --mode task` for touched areas, concurrency tests (10×) and the task's own
  `verify` commands. The Stop hook keeps the executor working until `verify` passes on a clean tree with `status: review`
  and background work settled.

## The fence

The fence lives in git hooks and trusted CI, so every harness gets the same limits. Unified harness adapters
(`scripts/agents/agent-hook.mjs` wired via `.claude/settings.json` for Claude Code, `.agents/hooks.json` for
Antigravity, and `.opencode/plugins/app-guard/index.mjs` + `opencode.jsonc` for OpenCode) resolve role from worktree `agent-role`
and stop forbidden calls before execution:

- Orchestrators work in the main checkout without executor restrictions.
- Protected files (rules, gates, dependency manifests, ADRs, the design-kit primitives…) are listed in
  `scripts/agents/lib.mjs`. A task opens one with `unlock:` only when the planner means it.
- Generated files (OpenAPI document, Kubb client, route tree) are always allowed in commits when regenerated by their
  tools, never edited by hand.
- Existing EF Core migrations are append-only.
- The fence has no environment-variable bypass: reviewers polish within `allow` in `review/NNNN-slug`; changes outside
  `allow` require a new task or an orchestrator commit on `main` after merge.
